# PR 610: inversion of control 

81 commits, 37 tickets, 142 files, +24,116 / -1,146. Baseline is `origin/main` at
`770ae565`. Nine new verbs: `install`, `sop`, `profile`, `conductor`, `candidate`,
`worker`, `evidence`, `attachments`, `attachment`.

# TL;DR - the coming tokenpocalypse

Anthropic and OpenAI released frontier models, Fable 5 (v2) and Sol respectively, that took more liberties when implementing tickets than previous models. Put a different way, they tend to go off the rails and ignore instructions, and needed more guardrails to continue using them productively.

This was coupled with work to invert primary invocation from CLI to in-CLI - build is primary used as a tool by agents instead of build invoking agents. Anthropic's announcement, since suspended, that -p would be charged at API rates. The sentiment is clear - if you want to use frontier models to code, you will do so within a walled garden or pay API rates. I developed a workaround, but there's no time to play whack-a-mole. 

A glossary of the terms used below is at the end of this document.

## SOP text moved from loose files into the binary

Before: the run-backlog and cross-impact SOPs were markdown files copied between
repositories by hand. Build did not read them, did not version them, and could not
detect that two clones on the same binary held different process text.

Now: SOP text is compiled into the binary as embedded resources and described by a
static catalog (`SopBundleCatalog`). Each catalog entry lists its target paths and
classifies each one as **emitted** (content owned by the catalog, validated
byte-for-byte against a recorded SHA-256) or **scaffolded** (path owned by the
catalog, content owned by the repository, never overwritten after creation).

- `build sop install` writes emitted stubs and scaffolds `.build/conductor.toml`.
- `build sop doctor` recomputes each emitted stub's hash and reports drift.
- `build sop upgrade` rewrites only emitted files whose current content still
  matches a trusted previous hash embedded in the new binary.
- `build sop status` reports installed-versus-catalog state.

The SOP version is the binary version. There is no separate SOP release.

Two fail-closed behaviours are load-bearing. `sop doctor` scopes manifestless stub
checks by asking git which catalog paths are tracked; previously every git failure
collapsed to an empty list, so a missing git binary was indistinguishable from an
empty index and doctor reported clean. It now distinguishes the two and reports
`scope_unavailable`. Separately, every catalog target and the manifest path resolve
strictly below the repository root and are refused if any existing path segment is a
symlink or reparse point, checked before a write or delete is attempted.

## `build install` replaces manual configuration

Before: no install verb. Bringing up a new repository meant hand-writing
`.build/config.toml` and `.build/conductor.toml`.

Now: a three-stage sequence, each stage re-runnable:

```sh
build install                                      # stage 1: config, then emit profile prompt
build install --profile .build/profile.json        # stage 2: gate + SOPs, then emit invariant prompt
build install --invariants .build/invariants.toml  # stage 3: readiness preflight, prints READY
```

> Note: This workflow is directly due to Anthropic's -p announcement.

Repository facts are derived rather than supplied: `ticket_prefix` and `source_roots`
from repository contents, `branch_prefix` from local and remote branch naming,
`architecture_map` from tracked architecture documents. A fact that cannot be derived
is written as an explicit sentinel string that `sop doctor` rejects, not as a default
value. This distinguishes "unset" from "set to a guess", which the previous scaffolder
could not do.

Stage 3 prints READY only after `sop doctor` passes, configured checks resolve,
conductor data loads, the branch is clean and not protected, no merge or rebase is in
progress, and `build worktree list` answers. It does not install target-stack
dependencies and does not require a green target build.

Stage 2 is atomic: an SOP install failure rolls back that stage's config and conductor
writes, preserves the local stub, and names both the reason and the command to rerun.

## The no-worker verb band expanded from three verbs to ten

Build's original execution model spawns an agent worker for LLM phases. Worker-spawning
verbs (`chain`, `implement`, `review`, `plan`) refuse to start inside an agent session,
so an already-running agent could not drive any step requiring judgment.

The verbs that load only the config sections they consume, without requiring
`[ticketing]`, `[workers]`, or `[events]`, without resolving ticketing secrets, and
without constructing a Plane client, were `worktree`, `gate`, and `waves`. Added:
`candidate status`, `sop`, `worker brief`, `evidence`, `profile`, `conductor`, and
`install`.

These establish a prompt-and-apply pattern for steps that need a model:

```sh
build profile prompt | agent > profile.json && build profile apply profile.json
build conductor prompt | agent > invariants.toml && build conductor apply invariants.toml
```

Build emits a fixed prompt and exits. An external agent produces JSON or TOML. Build
validates that output against a schema and applies it, or refuses with a nonzero exit.
No worker is spawned at any point, so the sequence runs inside an existing agent
session.

Supporting primitives for an external orchestrator:

- `build candidate status --ticket <id> --base <ref>` emits SHA-256 fingerprints of
  the tracked diff, the cached/index diff, and untracked content, plus touched paths,
  branch, head/base SHAs, dirty state, and lease metadata.
- `build worker brief --ticket <id> --role implement|review|rework` writes the brief an
  agent would have received as a Markdown artifact, without spawning the agent.
- `build evidence add --kind claim|review|commit|integrate|gate|final` posts one
  structured comment and reads it back by id. It never transitions a ticket.

## Gating checks are now proven against canaries before being written

Before: `.build/config.toml` could declare review checks and nothing verified they
could fail. A config with zero gating checks passed every ticket.

Now: `build profile apply` runs `ProfileGateVerifier` before writing config. It creates
a throwaway worktree at HEAD, runs the profile's `install_command`, runs all setup and
gating checks once to confirm they pass on clean source, then for each gating check
invokes `GateVacuityProver`: materialize that check's declared canary file, re-run only
that check, and assert it now fails. Any gating check that stays green against its own
canary blocks the write. A profile declaring no gating check is rejected outright.

`--skip-canary` is the explicit opt-out for constrained machines and records that the
proof was skipped. `build profile verify-canaries` runs the same proof without writing.

The canary is data on the `CheckSpec`, not engine logic: `CanaryFile(Path, Content)` is
supplied by the deriving agent, so the engine never encodes what "broken" means for any
stack.

Separately, `AutomatedChecksRunner` now redirects and closes stdin for every check.
Previously checks inherited the caller's stdin handle. From a terminal that is a
readable console; from an agent harness it can be a handle Windows reports as
redirected and then fails reads on with `ERROR_INVALID_HANDLE`. The same test suite
therefore passed in a shell and failed under an agent. Every check now reads EOF
identically in all three contexts, and a check that prompts fails fast instead of
blocking to its timeout.

## Stack-specific logic removed from the engine

`ConfigProfileWriter`'s clobber gate classified a review check as hand-customized if its
executable was not the literal string `"dotnet"`. On any other stack, install stage 2
read its own stage-1 output as customized and exited 1, so the idempotent path was
unreachable and installation could not be repeated.

The gate is now computed from the transform result: a config already matching the
profile returns `AlreadyMatched` without consulting the gate, and the gate fires only
when an existing run of check entries would be replaced with different content. Adding
checks where none existed is never a clobber. Tests cover dotnet, go, npm, make, and
swift, so reintroducing an executable-name literal fails the suite.

Related: `install_command` must be frozen and non-mutating. A bare `npm install`
renormalizes the lockfile per platform, which dirties a tracked file in every leased
worktree it hydrates and fails the baseline tracked-state check before any ticket is
claimed. The derivation prompt now states the constraint and gives the frozen form per
ecosystem.

## Ticket I/O corrections

- Plane comment reads are paginated. Previously only the first page was returned, so a
  long ticket silently lost history.
- `build attachments <ticket>` lists work-item attachments and inline description
  images, deduplicated by asset UUID. `build attachment <ticket> <asset-id> --output
  <path>` downloads one. Binary is never written to stdout, an existing path is never
  overwritten, and a failed download leaves no partial file.
- The Plane token resolves from `plane_api_token`, then `plane_api_token_env`, then
  `plane_api_token_file`, then fails naming every source tried. The file source is what
  makes Build usable from a process with no login shell, since `bash` sources
  `~/.bashrc` only for interactive shells and `zsh -c` does not read `~/.zshrc`.
- `.build/config.toml` is now tracked, because it carries repository facts that must
  travel with a clone. `InlineTokenScanner`, used by `sop doctor` and `setup --check`,
  rejects a literal token before it can be committed.
- `sop doctor` and `sop brief` previously failed inside every linked worktree. One
  worktree-aware resolver now answers for config, conductor, and catalog paths.
  `.build/` is per clone, not per worktree; resolution never climbs past the repository,
  so a repository with no `.build/config.toml` fails closed instead of adopting an
  ancestor's.

# Glossary

Terms are defined as this codebase uses them, which is not always the industry-general
sense.

### Process and SOP terms

**SOP** - Standard Operating Procedure. A process document that instructs an
orchestrating agent how to perform a multi-step workflow. Two ship in the binary:
`run-backlog` (claim tickets, implement, review, integrate) and `cross-impact` (assess
a change's effect across repositories). An SOP is text for an agent to follow, not code
Build executes.

**Catalog** - the static, compiled-in description of every SOP: its text resources, its
target paths, and the expected SHA-256 of each emitted file. `SopBundleCatalog` in
`ThroughlineBuild.Contracts`. The catalog is the authority for what is correct.

**Emitted path** - a file whose *content* the catalog owns, such as
`.claude/commands/run-backlog.md`. Validated byte-for-byte against the catalog hash.
Editing it locally is drift.

**Scaffolded path** - a file whose *path* the catalog owns but whose content the
repository owns, such as `.build/conductor.toml`. Created once if absent, never
overwritten, validated by shape rather than by hash.

**Host stub** - a small emitted file that makes an SOP invocable from a specific agent
tool. `.claude/commands/*.md` for Claude Code, `.agents/skills/*/SKILL.md` for Codex.
The stub points at the SOP; it is not the SOP text itself.

**Manifest** - `.build/sop-manifest.json`, a record of what a previous install wrote.
It is a cache used to find files, never authority for what those files should contain
and never permission to modify an arbitrary path.

**Drift** - an emitted file on disk whose content no longer matches the catalog hash.

### Command-shape terms

**doctor** - a read-only validation verb that reports findings and never mutates.
Convention borrowed from `brew doctor`.

**`sop doctor`** - specifically: reads `.build/conductor.toml`, validates it against the
conductor schema (unknown keys are findings, so a misspelled field cannot be silently
ignored), verifies every emitted stub byte-for-byte against the catalog, and reads
`.build/config.toml` only for `[[review.checks]]`. It runs without ticketing
credentials, worker config, or event config, so missing secrets do not block it. It is
the readiness check `build install` stage 3 must pass.

**brief** - **two distinct meanings, disambiguate by verb.**
`build sop brief <name>` prints an SOP's text plus resolved conductor data for an agent
to consume. `build worker brief` writes a per-ticket Markdown work order (ticket body,
acceptance criteria, diff, prior findings) that an implement/review/rework agent would
have been handed.

**prompt / apply** - a two-verb pattern for steps needing a model. `<verb> prompt`
prints a fixed instruction text and exits; an external agent answers it; `<verb> apply`
validates and commits that answer. Used by `profile` and `conductor`.

### Gate and check terms

**Check** - one configured command with a name, executable, arguments, and timeout
(`CheckSpec`). Declared in `.build/config.toml` under `[[review.checks]]`.

**Check role** - one of three values (`CheckRole`):
- **Gating** - failure blocks. These are the gate.
- **Advisory** - failure is reported to the reviewer but cannot alone force rework.
- **Setup** - preparation run before other checks; ordered first regardless of position,
  hard-fails on nonzero, and is exempt from canary proving.

**Gate** - **two related meanings.** (1) The verb `build gate`, which runs configured
review checks in the current directory. (2) The set of gating checks collectively, as
in "the gate can fail". A third, informal use appears in `AGENTS.md`, where "gates" means
the repo's own required `dotnet build` and `dotnet test`.

**Canary** - a deliberately broken file that a gating check *must* reject.
`CanaryFile(Path, Content)`, declared as data in the profile. It is how Build proves a
check is capable of failing. Content is supplied by the deriving agent, so the engine
never encodes what "broken" means for a given language.

**Vacuity / vacuous pass** - a check that reports green without actually testing
anything: no test files, a misconfigured runner, or zero configured checks. A vacuous
gate passes everything, which is worse than no gate because it looks like coverage.
`GateVacuityProver` is the component that disproves it, by materializing the canary and
asserting the check flips to red.

**Clobber gate** - the refusal that stops `profile apply` overwriting review checks a
human wrote by hand. Overridden with `--force`.

**Profile** - `PROJECT_PROFILE` JSON describing a repository's build, test, and lint
commands, their roles, their canaries, and the repository's `install_command`. Derived
per repository by an agent; applied into `.build/config.toml` by `build profile apply`.

### Conductor terms

**Conductor** - the orchestrator that drives a backlog run: decides which tickets to
claim, leases worktrees, dispatches workers, integrates results. Can be Build itself
(`build chain`) or an external agent ("bring your own conductor").

**`.build/conductor.toml`** - machine-local, gitignored conductor data: derived
repository facts (`branch_prefix`, `ticket_prefix`, `source_roots`, `architecture_map`,
`rework_cap`) plus review invariants and escalation rules. Recreated per clone by
`build install` or `build sop install`. Contains no secrets.

**Invariant** - a durable, repository-specific rule a reviewer must check on every
change, expressed as structured prose with an `id`, a `statement`, the `paths` it
applies to, and whether it `blocks_done`. Example from this repo: "Gate, scaffold, and
verification changes preserve a real failing path; zero configured checks never report a
silent pass." Build validates an invariant's *shape and surfacing*, never the truth of
its statement.

**Admission** - a run mode of `sop brief` for inspecting a candidate tree that Build did
not create. Takes a validated absolute inspection root (which must be a git worktree root
in the invoking repository) and a full 40-character SHA. While admission is active,
mutating verbs refuse before config bootstrap with error code `sop_admission_refused`.

### Worktree and run terms

**Lease** - an isolated git worktree plus helper branch, claimed for one ticket via
`build worktree lease --ticket <id>` and recorded in a manifest. Parallel workers each
get their own lease so they cannot clobber each other's HEAD.

**Helper branch** - the branch created for a lease, named from the ticket and
`branch_prefix`.

**Teardown** - `build worktree teardown`, which removes a lease. Refuses to discard
unmerged or dirty work unless `--force`, and can be required to prove the helper branch
merged into a named ref first.

**Wave** - a batch of tickets scheduled to run in parallel because they neither depend on
one another nor touch conflicting paths. `build waves` computes the schedule and reports
why any ticket was serialized.

**Candidate** - the worktree state produced by a worker, before review or integration.

**Fingerprint** - the set of SHA-256 hashes from `build candidate status` that identify
exactly what a candidate changed, letting an orchestrator prove the tree it reviews is
the tree the worker produced.

**Evidence** - a structured audit comment posted to a ticket by `build evidence add`,
recording a claim, review verdict, commit, integration, gate result, or final state. It
is an audit record only and never changes ticket state.

**Residue** - tracked files modified by the gate run itself, usually a regenerated
lockfile. Distinguished from a check failure: residue in regenerable host-dependent files
is reverted and re-gated once, residue in tracked source stops the run.

### Backend terms

**Plane** - the ticket backend (plane.so). Tickets here are `TLB-NNN`.

**Worker** - an external agent CLI (`claude-code`, `codex`, `gemini`, `copilot`) that
Build spawns to perform an LLM phase. Worker-spawning verbs refuse to start inside an
existing agent session, which is why the no-worker verb band exists.

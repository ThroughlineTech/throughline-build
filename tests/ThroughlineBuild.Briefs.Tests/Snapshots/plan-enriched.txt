# Plan: TLB-SNAP - Snapshot fixture ticket

You are an autonomous agent investigating a ticket and writing an implementation plan. You will explore the codebase, understand the problem deeply, and propose a concrete solution. Do not make code changes; investigation only.

## Ticket

**Title:** Snapshot fixture ticket
**Type:** feature
**Description:**

<h2>Plan</h2><p>Implement the fixture feature.</p><ul><li>Step 1</li><li>Step 2</li></ul>

## Repository context

**Main branch SHA at planning time:** abc1234567890def
**Top-level repo entries:** src, tests, docs, README.md



## Your job

Produce a complete investigation and implementation plan that a separate implementing agent can execute without guessing. The plan you produce will be appended to the ticket's description in Plane and serve as the contract for the implement phase.

### 1. Understand the project context

- Read `CLAUDE.md` if it exists in the repo root.
- Read any context docs referenced above under "Project notes" or in `CLAUDE.md`.
- If the ticket description mentions a parent ticket, plan ticket, or op-doc, read that document to understand the scoping context. Do not expand scope beyond this single ticket - the parent provides framing, not work.

### 2. Deep-dive the relevant code

- Start from the locations the project context names as key source areas.
- Search the codebase for all files related to the ticket's domain. Use Grep, Glob, and Read aggressively.
- Read every relevant file end-to-end. Do not skim. Skimming produces vague plans.
- Map the call chain end-to-end: entry point -> business logic -> data layer.
- Identify the interfaces, types, and contracts the change will touch. Note existing test coverage.

### 3. Investigation depth by ticket type

- **For bugs:** trace the code path that produces the wrong behavior. Identify the root cause - the actual line, function, or contract that is wrong. "Probably something in the foo module" is not a root cause.
- **For features:** identify where the new code fits. Which interfaces extend? Which new files? Which existing patterns to follow? Which to deliberately diverge from?
- **For refactors:** map the call sites that depend on the surface being refactored. Identify whether the refactor is purely mechanical or has semantic impact.

### 4. Verify environment state

- If the project context names build, test, or install commands, run a representative one (e.g. `npm test`, `dotnet build`) to confirm the environment is in a workable state before planning against it.
- If you find environment gaps (missing files referenced by config, broken shims, stale lockfiles), note them in the Investigation section but do NOT fix them as part of this plan unless they directly block the ticket's work. Environment fixes are separate tickets.

### 5. Identify regression risks

- Which tests cover the affected code?
- Which user-facing flows touch it?
- What could break?
- What downstream callers or consumers might be affected?

## Output structure

Produce the plan as HTML for Plane. Structure with these sections, in this order:

```html
<h3>Investigation</h3>
<p>What you found, with specific file paths and line numbers. No vague descriptions.</p>
<p>Root cause (for bugs) or architectural fit (for features) - specific.</p>
<p>Regression risk assessment.</p>

<h3>Proposed Solution</h3>
<p>Approach, tradeoffs, and why this approach over alternatives.</p>
<p>If multiple paths exist, name them and explain the recommendation with reasoning.</p>

<h3>Implementation Plan</h3>
<p>One paragraph: what, why, approach.</p>
<p><strong>Relevant files</strong></p>
<ul><li><code>path/to/file.ts</code> - what changes</li></ul>
<p><strong>Steps</strong></p>
<ol><li>Concrete actions an implementer takes; numbered.</li></ol>
<p><strong>Verification</strong></p>
<ul><li>Specific checks. Include at least one manual verification step for UI work.</li></ul>
<p><strong>Design decisions</strong></p>
<ul><li>Decisions made during this investigation that the implementer should treat as settled. Include rationale for non-obvious choices.</li></ul>
<p><strong>Escalation rules</strong> (raise a ticket, do not work around)</p>
<ul><li>Name the adjacent fixes, refactors, or temptations the implementing agent must not take. Being explicit here preempts scope creep.</li></ul>
<p><strong>Out of scope</strong></p>
<ul><li>Explicit deferrals - work that belongs to a different ticket or a future phase.</li></ul>
<p><strong>Agent size:</strong> {S|M|L} - {inference rationale}</p>
```

**Plane render rule:** all `<ul>` and `<ol>` content goes on a single line. No newlines between list items. Plane renders inner newlines as empty bullets.

**Length target:** aim for under ~90 lines of rendered text, but completeness wins over brevity. An implementing agent should not have to guess. The `Relevant files` section is load-bearing for downstream drift detection - do not omit it.

## Discipline passes (mandatory)

After drafting the plan above and BEFORE returning the result, perform these two passes:

### Subtract pass

Review your own draft. Answer in the Investigation section (or add a short "Subtract pass" note):

- What can be cut? (items not needed to satisfy the ticket's acceptance criteria)
- What can be deferred to a follow-up ticket?
- Does this plan give an implementor enough detail without padding?
- Any `Relevant file` exceed the project's size ceiling (if one is documented)?
- Bundling a delight feature with a bug fix? Recommend splitting if so.

Document the answer (or a "nothing to cut" one-liner) before returning the result.

### Rubber-duck pass (load-bearing)

Read every shell, test, and build command in the Steps and Verification sections and ask "what happens when this actually runs":

- **Interpreter match:** does the test command use the right runtime for the script type (`bash` for `.sh`, `python3` for `.py`)?
- **Input feeding:** for piped stdin (`printf ... | cmd`, heredocs), do the bytes include the trailing newlines the tested code expects?
- **Path / file existence:** does every file path mentioned in Steps resolve to a real or about-to-be-created location? Grep-verify any referenced function or flag before posting the plan.
- **Reviewer simulation:** ask "if a reviewer looked at the Verification section, what would they flag?"

Document a one-line "Rubber-duck pass: clean" note in the Investigation section (or list any defects caught and fixed) before returning the result.

## Agent size inference

After drafting the Implementation Plan, count the Relevant files and Steps. Apply this heuristic:

- **S:** 1-2 files AND <=4 steps AND no new files; localized additive change; no load-bearing interface modifications.
- **M:** 4-6 files OR 6-10 steps; moderate cross-cutting change; or introduces new files.
- **L:** 7+ files OR 11+ steps; architectural change; modifies load-bearing interfaces; or high blast radius.

The "Agent size:" line at the end of the Implementation Plan section must match this inference.

## Invalid or already-fixed discovery

If investigation reveals the ticket is invalid, obsolete, or already fixed, return a WorkerResult with `Status = Escalate` and `FailureReason` containing a one-line explanation of what you found. Do not append a plan. The orchestrator will leave the ticket in Planning state for the operator to decide whether to `build close` (wontfix) or `build defer`.

## WORKER_RESULT envelope

When you have completed the investigation, the discipline passes, and the size inference, emit the result envelope as the LAST thing in your output. Use exactly this format - a bare `WORKER_RESULT` marker on its own line followed by JSON on the next non-empty line:

```
WORKER_RESULT
{
  "status": "Ok",
  "summary": "<one-line root cause or approach>",
  "files_changed": [],
  "failure_reason": null,
  "metadata": {
    "plan_html": "<the full HTML block from the Output Structure section above, escaped for JSON>",
    "risk_label": "<low|medium|high>",
    "size_label": "<S|M|L>",
    "planned_at_sha": "abc1234567890def"
  }
}
```

The `plan_html` field is the complete HTML you would have appended to the ticket's description. The orchestrator appends it to Plane. The `risk_label` and `size_label` fields drive Plane label application. The `planned_at_sha` field drives downstream drift detection.

## Rules

- Investigation only. Do not make code changes. Do not create branches.
- Reference specific file paths and line numbers. No vague descriptions.
- The `Relevant files` list is load-bearing for downstream drift detection. Do not skip it.
- The `Agent size` line is load-bearing for downstream model dispatch. Do not omit or hardcode it.
- Never mention specific model names (haiku, sonnet, opus, claude-*) in the size line or rationale - only S, M, L.
- The `[planned_at: SHA]` semantics are handled by the orchestrator after you return; do not embed the marker comment in `plan_html`.
- Do not propose work outside the ticket's scope; surface as "Out of scope" items instead.

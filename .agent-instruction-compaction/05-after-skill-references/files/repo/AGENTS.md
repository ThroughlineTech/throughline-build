# AGENTS.md - Throughline Build

Read this before touching the repo. It is the tool-agnostic contract for
agents, `build` workers, and humans. Agent-specific files only point back here.
Nested `AGENTS.md` files add local detail and win inside their subtree.

## Repository

Throughline Build is a .NET 10 Native AOT CLI named `build` for Agile ticket
workflow automation. Deterministic C# owns state, gates, git operations, and
ticket I/O; LLM phases (`plan`, `implement`, `review`, `decompose`) run in
external worker CLIs (`claude-code`, `codex`, `gemini`, `copilot`) selected by
config or `--agent`.

Design constraint: generated output is stack-agnostic. The engine may target
TypeScript, .NET, Python, or documents; stack knowledge belongs in derived data
(config, profiles, briefs), not hardcoded engine logic.

## Build And Test

Requires the .NET 10 SDK, `git` on `PATH`, and a native toolchain for Native AOT
publish (MSVC on Windows, Xcode CLT on macOS, clang/gcc on Linux).

```sh
dotnet build throughline-build.sln --nologo -v q
dotnet test --nologo -v q --logger "console;verbosity=minimal"
./build.sh
RID=osx-arm64 ./build.sh
dotnet publish src/ThroughlineBuild.Cli -r linux-x64 -c Release --nologo -v q
```

Gates for any code change: `dotnet build` and full `dotnet test`, both green,
with output pasted verbatim. Do not report done from a partial or filtered run.
CI restores, tests, and publishes on `osx-arm64`, `win-x64`, and `linux-x64`.

A fresh clone has no binary or backend config: `bin/` and `.build/` are
gitignored. Build the binary before using it. Root `Directory.Build.props` and
`Directory.Build.targets` are machine-local AOT linker overrides; tracked
`tests/Directory.Build.props` chains to them only when they exist.

## Working Rules

- Read before writing. Do not propose or change code you have not read.
- Branches: use `ticket/<id>` or a short descriptive branch; never commit
  directly to `main`.
- Commits: use `{TICKET-ID}: short description` for tickets, `topic: short
  description` otherwise. No agent-vendor branding, sign-offs, or generated-with
  lines.
- Implementing and shipping are separate. Do not merge, push to `main`, tag, or
  release without explicit instruction.
- ASCII only in anything you write: code, comments, docs, commit messages, and
  ticket bodies. Avoid em/en dashes and curly quotes. For existing non-ASCII
  bodies, read-modify-write through a file rather than a shell variable.
- Parallel work needs separate worktrees; never let two agents edit one working
  tree concurrently.

## Code Rules

- AOT: `ThroughlineBuild.Cli` publishes with `PublishAot=true`. Use
  source-generated `JsonSerializerContext`; never rely on reflection-based
  serialization. Keep `ThroughlineBuild.Contracts` I/O-free. AOT-sensitive tests
  must flip reflection off explicitly; see [tests/AGENTS.md](tests/AGENTS.md).
- The solution file is the source of truth for projects. Directories under
  `src/` that are absent from `throughline-build.sln` are local debris.
- Tests are per-project: each `src/` library has a mirrored suite under `tests/`
  with local fakes. Reuse the local doubles.
- Gates must be able to fail. Zero gating checks silently pass; when touching
  gate, scaffold, or verification code, confirm the failure path still fails.

## Ticket Workflow

This repo tracks Plane tickets (`TLB-NNN`) through the `build` CLI it builds.
That path requires a configured backend. `.build/config.toml` is gitignored; in
a fresh clone, run `build init` and `build setup`, or use GitHub issues/PRs
instead.

When a backend is configured, all ticket operations go through `build`. No direct
REST, MCP ticket server, or `/ticket-*` slash-command path is allowed. Add
`--json` for the versioned stdout envelope
(`{schemaVersion, ok, data}` or `{ok:false, error:{code, message}}`); diagnostics
go to stderr. Exit codes: 0 ok, 1 failure, 2 usage/config, 3 missing secret.

| Intent | Command |
| --- | --- |
| list tickets | `build list [--state Backlog] [--json]` |
| read ticket | `build get TLB-N [--json]` |
| create ticket | `build new --print-template > draft.md`, fill it in, then `build new draft.md`; JSON drafts may pipe to `build new - --json` |
| read comments | `build comments TLB-N [--json]` |
| comment | `build comment TLB-N - [--json]` |
| move state | `build transition TLB-N InProgress [--json]` |
| relations | `build relate TLB-N blocked_by TLB-M [--json]`; `--list`; `--remove <RELATION-ID>` |
| close/defer/reopen | `build close\|defer\|reopen TLB-N "reason" [--json]` |
| amend | `build amend TLB-N <option> ... [--json]` |

Bare numbers expand in the configured project: `35` means `TLB-35`. Use
`build --help` and `build <verb> --help` for exact flags and formats.

Composite intents:

- Investigate ticket N: `build get TLB-N`, read comments, investigate with your
  own tools, then write findings with `build comment TLB-N - --json`.
- Work on ticket N: read ticket and comments, implement normally, run gates,
  then `build comment` and `build transition`. The autonomous terminal pipeline
  is `build chain TLB-N`.
- Create tickets with `build new --print-template`; its headings match validator
  expectations for title, acceptance criteria, and out-of-scope content.

## Repo Hazards

- You edit the tool you use. Before live backend mutations while changing a
  ticket verb, client, transport, retry, state-transition, or serialization path,
  verify read-only behavior, inspect JSON envelopes and exit codes, avoid chained
  mutations, and save final ticket updates for a freshly built known-good binary.
- Worker-spawning verbs do not nest. `build chain`, `build implement`,
  `build review`, and `build plan` launch agent CLIs that refuse to start inside
  an agent session. Agents should run deterministic verbs directly and leave
  worker-spawning verbs to a plain terminal.
